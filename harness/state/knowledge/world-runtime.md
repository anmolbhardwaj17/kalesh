# world-runtime

Streaming and world runtime: one line per gotcha, added by builders as they hit them (area in docs/READ_MAP.md "Streaming and world runtime").

- Streamed city (P1-019): `--tiles=test` or `--tiles=full` adds `World/City` (`game/world/world_stream.gd`, group `world_stream`) with the core as its first child `Stream`. Tests build it with `WorldStream.new().setup(dir)`, `core.set_process(false)` and step it by hand (`core.step()`); `core.warp(pos)` loads in a burst, `core.set_focus(pos)` under the play caps.
- Headless Godot cannot make meshes on worker threads: the dummy renderer's mesh storage is not thread safe ("Attempting to initialize the wrong RID", "Parameter mem is null" from `servers/rendering/dummy/storage/mesh_storage.h`, about 1 test run in 8). `stream_core.gd` reads on the main thread when the display server is headless; a threaded unit test may use only systems that make no mesh (colliders, lanes). Windowed, 540 threaded reads raised nothing.
- Never `free()` a node from an `_exit_tree` handler while its parent is leaving: the parent is busy removing children ("Parent node is busy", `Condition "data.parent" is true`), the node is deleted and the parent deletes it again: an abort at quit ("pointer being freed was not allocated"). `tile_mesh.gd dispose` frees a node that is in the tree and queues one that already left. Children leave last child first, so the core must stay the city's first child.
- A system's `prepare` runs on a worker thread, several tiles at once: it may read shared data (the stand-in materials made on the main thread) but never write it, and it returns resources only (ArrayMesh, shapes, arrays). A node made there would leak when a read is cancelled.
- Mesh bounds for the magnitude rule come from `ArrayMesh.get_aabb()` right after `add_surface_from_arrays` on the worker (free, no per-vertex script work); lane points and pins are checked in `tile_reader.gd`. Collider faces are not checked at load (the bake and its tests do).
- Mesh buffers made on a worker thread reach the GPU when the main thread next calls the RenderingServer: one flush of up to 3.5 ms for a dense tile, inside the mesh attach step or at the draw. It is why `ground_roads:attach` sometimes reads 3.5 ms in `stream('info').worstStepMs` while frames stay under 11 ms.
- A ray finds a streamed collider on the frame after its chunk attached: the teleport's ground ray runs one process frame after the ring is live and hit every time (4 places, 12 teleports in a row). Not tried with the sim held.
- Tile counts round a point: 13 to 16 tiles inside the 375 m ring, up to about 24 held with the hysteresis band at 200 km/h (30 at time scale 4). A dense pilot tile has 40 to 58 collider chunks; the ring at Chandni Chowk is 558 chunks and attaches in 150 ms in a burst.
- Compare memory or object counts only in the same state: arrive from far away (a teleport to another district first), or tiles of the hysteresis band of the last place are still held (16 against 14 tiles at India Gate).
- `stream('path')` drives the stand-in car along world points on the sim tick; routes on real lanes come from `node tools/fixtures/gen_stream_routes.mjs` (rerun after a bake that changes `tiles.hash`, P1-036 was one; the scripts fail with that hint when the hash differs). The Connaught Place place of the fixture lies in tile -1_-8, outside the test block.
- `game/debug/debug_server.gd` only dispatches (440 lines after P1-040): put new hook code in its own file under `game/debug/` (as `stream_probe.gd`, `debug_perf.gd`, `debug_camera.gd`, `debug_input.gd`).
- City scene (P1-024): the streamed tiles are few nodes (a ground and roads node and a building node per tile, about 50 under World) and the colliders are PhysicsServer3D bodies with no node: a mirror or transform check must read the bodies (`body_get_state`) from `core.tiles[key].parts.colliders.bodies` (`city_probe.gd mirror`).
- Lane pieces chain through `next` only within their own lane (no lane changes): a route target must lie on the lane chain the start lane leads into, or Dijkstra goes round the block (the first ITO flyover route came out 7.4 km instead of 650 m). Pick targets on the start lane's chain (`tools/fixtures/gen_city_routes.mjs`).
- Access by mode in the game (P2-045): use `lane_router.gd usable(piece, mode)` (walkers: `foot` in the modes, or a car road at grade for its footpath) rather than raw `lanes.allows` when a walker is involved; find pieces near a point with `lanes.gd near/closest/closest_on` (a 32 m grid filled on attach, cells worked out in prepare), never by looping over every loaded piece (36k in the pilot; the router's first version took seconds that way).
- Lane `back` lists are often empty across junction paths: to find what leads into a piece search `next` links of the others (tools/fixtures or GDScript), never trust `back` alone. The walker search in `lanegraph.mjs walkRoute` joins pieces by their end points instead.
- A start pin on a car-free road is a violation by the auto on every boot: since P2-045 every drive from a pin in `gen_city_routes.mjs` checks `carFree` 0, and scripted walks skip pieces that cross a car-stopping bollard line (a walker does not thread 0.93 m gaps reliably).
- Buildings (P2-010): `buildings.gd cells_of` groups placements per module mesh and 125 m cell with index lists in plain Arrays (a PackedArray inside a Dictionary or Array is copied on append), then fills one PackedFloat32Array of 16 floats an instance (12 transform, colour r g b, wear). The MultiMesh resources are made in `prepare`; `attach` adds 40 nodes a step. Node names start `buildings_` so `stream('layers')` hides shells and modules together (it now matches GeometryInstance3D).
