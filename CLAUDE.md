# Dilli Darshan

A browser game built autonomously by Claude Code for Anmol. Anmol mentors; Claude builds, verifies and never waits (after Phase 0, which waits for Anmol by design). This repo is a new game started with the harness kit on a minimal scaffold (a box car on a ground plane with the hook contract). The old driving game is a read-only reference: see "Game facts" at the end.

## Rules for every agent

1. **Never wait for Anmol** (after Phase 0). Do not ask him questions and stop. Make the best call, record it in `harness/state/decisions.md` (date, decision, why), and continue. Things only he can provide (art files, voice files, playtest feel, deploy login) are requested through the dashboard and never block work. Why: the build runs for days unattended; a question that waits for an answer stops the whole loop. Phase 0 is the one exception: the style is his call and is asked for on purpose (see Phase 0 below).
2. **Never block on art or audio.** Reference assets by id; register new needs with `assets.mjs`; the game uses procedural placeholders until files arrive. Why: art arrives in batches when Anmol has time; code that waits for it never ships.
3. **Evidence or it did not happen.** A task is done only when its acceptance criteria are shown true by commands, tests or screenshots that someone actually looked at (Read the PNG). Why: "it should work" claims are where regressions hide; a verifier that reads the shot catches what a passing script misses.
4. **Stay in the repo.** No sudo, no global installs (except `npx playwright install chromium`), no edits outside this folder, no force pushes, no history rewrites. To discard a failed attempt use `git stash push -u -m "<task id> failed attempt"` (recoverable), never `git reset --hard`. Why: everything must be recoverable and the machine is Anmol's. `.claude/hooks/guard.mjs` blocks the worst of these.
5. **Writing style for anything Anmol or players read** (dashboard text, journal, inbox replies, playtest checklists, docs, dialogue): plain direct English, short sentences, **no em dashes** (use commas, colons or separate sentences).
6. **Keep learning in files**, not in context: gotchas to `harness/state/knowledge/<area>.md` (one line each; `knowledge.md` core only for cross-cutting ones), architecture choices to `decisions.md`, module map to `docs/ARCHITECTURE.md`. Why: context is compacted and sessions restart; files survive both.
7. **No Claude attribution in git.** Commit messages and PR descriptions never carry a Claude co-author line or a "Generated with Claude Code" footer. `.claude/settings.json` sets `attribution` to empty, and the versioned `commit-msg` hook in `.githooks/` (enabled with `git config core.hooksPath .githooks`) strips any such line. Why: Anmol's history, Anmol's name.
8. **GitHub.** Remote `origin`: none yet, branch main. Until Anmol creates it, add one Needs-you notice (`node harness/bin/notice.mjs add "Please create a private GitHub repo for Dilli Darshan and tell me its URL"`, only if no such notice is open), skip the push and keep working; never create the remote or change visibility yourself. Once he gives the URL: `git remote add origin <url>`, update this rule, resolve the notice. Then push after every verified commit (`git push origin main --follow-tags`). If a push fails, do not wait: add a Needs-you note on the dashboard (`node harness/bin/notice.mjs add "<text>"`, resolve it once a push works) and keep working. Never commit files over 50 MB, secrets or `.env` files. Why: an off-machine copy after every verified step; a failed push must be visible without stopping work.

## Modes (switchable)

Anmol switches these by telling the orchestrator (record the switch in decisions.md with the date and his words). The current setting is the one marked ON.

- **ONE AGENT AT A TIME: ON.** Only one subagent runs at any moment, builder or verifier or any other. No Lane 2, no building while a verifier checks a snapshot, no run-ahead or parallel content or art agents. This overrides the Parallel, Run ahead, Verify on a snapshot (the next builder waits for the verifier) and Lane 2 rules below. Why: one agent at a time keeps usage predictable and avoids two agents fighting over the GPU and the working tree. Turn OFF when Anmol asks for more speed.
- **LOW USAGE MODE: ON.** Overrides every rule below that asks for more testing:
  - Batch: one builder run per related group of small tasks, one verifier for the group.
  - Builder: runs only the scenarios its task names, plus `verify --quick` once at the end. No flakecheck unless a scenario fails, then 3 runs at most (camera tasks too). No extra probes or before and after comparisons beyond the acceptance. After 2 failed fix rounds on one problem, report instead of continuing.
  - Verifier: only for tasks judged by eye. Reuse the builder's quick report when fresh. Run the acceptance scenarios once, replay at most 2 milestones, read at most 6 images, no extra seeds or repeat flakechecks. Report under 40 lines.
  - Self-check (orchestrator, no agent) for anything judged by numbers or tests: typecheck, tests, quick, read the summary.
  - Flakes: a scenario that fails once and passes on one rerun is noted, not a task, unless the same one fails again at a phase gate.
  - Models: Opus for look, animation and hard bugs; Sonnet for tooling, data, small fixes and all verifiers (phase gates too unless a gate result is unclear).
  - Unchanged: `verify --all` at phase gates (machine time, few tokens).
  Why: on a smaller plan the tokens go to building, not to repeated checks. Turn OFF for the full-depth rules below.
- **LANE 2: OFF.** See "Lane 2" below.
- **MID-PHASE SWEEP: OFF.** See "Regression sweep" below.

## Phase 0: ADOPT, STYLE DISCOVERY and ARCHITECTURE DISCOVERY (waits for Anmol by design)

The harness starts on a game that already exists. Phase 0 makes the harness able to drive it, measures it, and agrees the style with Anmol before any look work. It is the only phase that waits for him. `task.mjs next` prints `PHASE_NEEDS_PLANNING P0` on the first run: spawn the planner with `PLAN_PHASE P0` (ADOPT mode). It writes the Phase 0 tasks; then the loop runs them in order.

**a. Read the existing repo** (planner ADOPT, then builders): engine and render pipeline, current look (shots), what exists and what is broken, perf on this machine. The first builder task implements the hook contract (`docs/GAME_HOOKS.md`: `window.__game` with state, clock, frames, input, perf, load, teleport, camera, time scale, sim hold, events, hud) behind `?debug=1`, so verify can drive the game. Then a verify baseline (scenarios and play scripts for what exists) and a measured perf baseline (`lookproof.mjs --set baseline --perf`) with draft budgets. Then the quality audit, `harness/design/QUALITY_AUDIT.md` ("why it feels thin"): an honest score against a polish and richness bar for visuals, feel (handling, speed sense, camera for a vehicle game), audio, VFX, life (traffic, people), UI and HUD, and performance, every finding with evidence. Anmol reads it before the style rounds, so the rounds aim at the real gaps. Why: an adopted game rarely fails one thing; it is thin in many small ways, and those must be named before choosing a look.

**b. Interview Anmol in rounds.** Tasks with agent `orchestrator` are yours (the main session), not a subagent's. Use AskUserQuestion when it is available, else plain questions in the terminal, and wait for the answers. Follow `harness/design/templates/STYLE_INTERVIEW.md` round by round: references (games, films, art, photos), mood, palette, lighting, camera, art style, what he does not want, target hardware, how assets will be made. Record every answer verbatim with `task.mjs inbox-add "<his words>" --source interview` and ack it, then pass the answers to the planner (STYLE_DISCOVERY).

**c. Compare candidate styles side by side.** The planner writes `harness/design/STYLE_OPTIONS.md` from `templates/STYLE_OPTIONS.template.md`: for each candidate (for example low poly flat, toon or cel, painterly, stylised PBR, realistic PBR, pixel art 3D, or what Anmol names) a comparison of look, feel, performance on this machine (draw calls, shader cost, frame time; estimated, then measured), asset pipeline (who makes what, AI image prompt fit, AI models), tooling, risk, scope and time, and fit with the existing code. Builders render each candidate as a switchable style test in the actual game (`?style=<name>`), and `lookproof.mjs --sheet` puts the shots side by side with measured frame times. Show Anmol the sheet (`harness/reports/look/style_options.jpg`) and the table.

**d. Loop until Anmol signs off explicitly.** A round: show, ask, record, refine (new candidates, mixes, tweaks, another test). Only his explicit words count as sign-off ("yes, go with toon B" counts; silence, "looks nice" or "maybe" do not: ask him to confirm). Record it with `node harness/bin/task.mjs signoff "<his exact words>"` (writes state.json and a decisions.md entry). Then the planner writes STYLE_BIBLE.md (from its template), the VERIFY.md look rules, signed budgets in `perf_budgets.json`, `look_rules.json`, and approves the chosen style's shots as the reference (`lookproof.mjs --approve <set>`). Use `templates/SIGNOFF_CHECKLIST.md` before marking the sign-off task done.

**Moving the game to a new place** (for example one city to another): the interview adds the place round (`templates/STYLE_INTERVIEW.md` 2b) and fills `CITY_BRIEF.md`; the comparison adds the fidelity options (stylised low-poly city, stylised realistic, realistic PBR with baked lighting, photo-textured) with honest costs for performance at play speed and asset volume; and after sign-off the first phase is a relocation phase (`templates/RELOCATE_PHASE.md`: inventory of place-specific assets with replace, reuse or remove; art batches; procedural-first placeholders so nothing waits for art).

**d2. Architecture discovery (mirrors c and d).** The planner (mode ARCH_DISCOVERY) writes `harness/design/ARCH_OPTIONS.md` from `templates/ARCH_OPTIONS.template.md`: one row per system decision (renderer, physics, world data, the map repair layer from `harness/design/MAP_REPAIR.md` with its sources and licences, the lane-level road model, the map inspector page, roads and junctions, terrain, streaming, instancing, LOD, textures, budgets), 2 to 4 options each, compared on measured performance on this machine, quality, complexity, risk, tooling and fit with the signed style. Builders write small bench scenes for the options that need measuring (`?arch=<name>` pages or `harness/bench/` scripts, numbers through `debug.perf` and written to `harness/reports/arch/<name>.json`). Show Anmol the table with the measured numbers and a recommendation, loop until he signs off in his own words, and record it with `node harness/bin/task.mjs archsignoff "<his exact words>"`. The planner then writes the chosen design into `harness/design/TECH.md` and `docs/ARCHITECTURE.md` and a decisions.md entry. The architecture sign-off covers the map repair layer too (sources, pipeline, rules, lane-level road model, map inspector, verification, pilot area). The map inspector is an early task right after the sign-off, so Anmol can review issues during the pilot. Style, architecture and game design rounds may run in the same interview turns; all three sign-offs are needed.

**d3. Game design discovery (mirrors c and d).** A car driving around Delhi is a tech demo, not a game. The planner (mode GAME_DESIGN_DISCOVERY) writes `harness/design/GAME_DESIGN_OPTIONS.md`: 2 to 4 candidate games built from what makes Delhi Delhi, each with its fantasy, core loop, pillars, a sample mission list and a progression plan, compared on fun, scope, risk and fit with the signed style and architecture. Interview Anmol round by round, record his words with `inbox-add --source interview`, loop until he signs off in his own words, and record it with `node harness/bin/task.mjs designsignoff "<his exact words>"`. The planner then writes the chosen design into `GAME.md` (fantasy, core loop, pillars, mission list, progression plan). Standing rules from then on: each phase is checked against the GAME.md pillars, every mission task's acceptance includes fun criteria (clear goal, fair fail, a reason to retry, a reward that matters) as well as function, and no mission system is built before this sign-off. Why: the tech and the look can be perfect and the game still not worth playing; the design is Anmol's call and is agreed up front.

**e. Only then plan the game** from its current state: the planner adds the next phases (`task.mjs phase-add`) and `task.mjs gate P0` checks all three sign-offs (style, architecture and game design; the gate and `gate --final` fail with a "No game design sign-off" reason until `designsignoff` is recorded). From here on the never-wait rule applies to everything.

Mentor messages during Phase 0 are handled as in step 2 of the loop; an answer that belongs to an interview round goes to the planner too.

## The loop (main session = orchestrator)

The main session is the orchestrator and runs under `/goal`. It delegates real work to subagents (`builder`, `verifier`, `planner`, `content-writer`, `art-director`, `art-reviewer`) so its own context stays small. It does not read source files or big docs itself; it reads command outputs and subagent summaries. Why: the orchestrator runs for days; every file it reads stays in its context and is resent on every turn.

Repeat until `node harness/bin/task.mjs gate --final` prints `ALL GATES PASSED`:

1. **Status.** `node harness/bin/task.mjs status`.
2. **Mentor first.** If Anmol typed a message in this terminal, record it verbatim: `task.mjs inbox-add "<his words>"`. If the inbox count is above 0: `task.mjs inbox`, then for each message decide and act:
   - direction change: update the design docs or data files, add a `decisions.md` entry, add or reprioritize tasks (`task.mjs add --priority 1 --kind mentor ...`), and spawn the planner in REPLAN mode if the active phase plan no longer fits;
   - bug or feel feedback: add a task (`--kind bug`, priority 1 or 2);
   - question: answer it in the reply;
   - a mode switch (one agent at a time, low usage, lane 2, sweeps): update "Modes" above and add a decisions.md entry.
   Then `task.mjs inbox-ack <id> --reply "<one or two lines>" --tasks <ids>`. Finish or cleanly stop the in-flight task before acting on a direction change. Why: Anmol's word changes what is worth building; acting on it first avoids building the wrong thing.
3. **Art pass.** If status says `art pass due: YES`, spawn `art-director` (it only touches `harness/requests/`, so it may run while a builder works when parallel agents are allowed). No final prompts before the style sign-off.
   **Art review.** If status says `art review due: YES`, spawn `art-reviewer` (one at a time). It checks every new upload, keeps what works, and for real problems rewrites the prompt and puts the card back as a redo (removing unusable files from the game). It never blocks tasks. It also checks game fit: does the art work on the model and where the game uses it (shop icon vs the item the player sees, portrait vs the character's in-game version, texture at the player's scale in a scene). It adds builder tasks when the code should change to match good art. When it returns, commit `harness/requests/` and `public/assets/` only. At every phase gate, also spawn it with `FIT RECHECK` so images whose game feature was not built yet get checked once it exists.
4. **Next.** `task.mjs next` and act on what it prints:
   - a TASK: `task.mjs start <id>`, then spawn the agent named in the task with the brief below and wait for its result. A task with agent `orchestrator` (Phase 0 interviews) is done by you: ask Anmol, record the answers, then `task.mjs done`.
   - `RESUME <id>`: look at `git status --short`; spawn the builder with "continue this task from the current working tree" plus the task text.
   - `PHASE_NEEDS_PLANNING <P>`: spawn `planner` with `PLAN_PHASE <P>` (for P0 this is ADOPT mode).
   - `PHASE_GATE <P>`: spawn `verifier` with `GATE <P>` (runs `verify.mjs --all`), then `task.mjs gate <P>`. If it passes: spawn `planner` with `PLAYTEST <P>` (writes the checklist via `task.mjs playtest`), run `task.mjs phase-done <P>`, `git tag phase-<P>`, and `git push --follow-tags` if a remote exists. If it fails: add fix tasks from the printed reasons.
   - **Gate retry:** after the fix tasks of a failed gate are done, the gate does not always need a new `verify --all`. `task.mjs gate <P>` keeps the phase's full run safe in `harness/reports/gate/<P>-all.json` and checks which path applies. If the files changed since that full run touch no shared-system path (listed in `harness/verify/shared_paths.json`), run `node harness/bin/gateretry.mjs <P>` (add `--flaky <names>` for items that failed only by chance; those get a flakecheck of 10 runs). It reruns each failed item, `verify --quick` and every playable milestone once and writes a retry report. Then run `task.mjs gate <P>` again: it passes on the retry when every failed item passes, quick is ok and every milestone is ok. If the fix touches shared code, the gate says so and lists the files: spawn the verifier with `GATE <P>` for a full `verify --all` as before. `gateretry.mjs <P> --dry` shows the plan and which path applies without running anything. Why: a narrow fix should not cost a multi-hour full run, but a shared-system change can break anything, so it still gets one.
   - `STUCK <P>`: spawn `planner` with `REPLAN` and the stuck list.
   - `ALL_PHASES_DONE`: spawn `verifier` with `GATE FINAL`, then `task.mjs gate --final`.
5. **Verify by tier.**
   - **Verifier tier:** tasks that change visuals, gameplay, scenes or milestones. Spawn `verifier` with the task id and its acceptance criteria (it runs `verify.mjs --quick`, plus `--milestone` or targeted `--only` runs, never `--all`).
   - **Self-check tier:** tooling, data, content, docs and pure-logic tasks. Verify it yourself: `npm run typecheck && npm test && node harness/bin/verify.mjs --quick`, and read the summary (and check the acceptance criteria with a command where one applies). Why: a verifier agent costs a full context; numbers and tests do not need eyes.
   - **Models and usage:** builders run on Opus; verifier, art-director and content-writer run on Sonnet. Spawn the verifier with `model: "opus"` for phase gates (`GATE <P>`, `GATE FINAL`) and for a task's third attempt (unless low usage mode says otherwise). Tell every agent to downscale shots and sheets to about 1600 px (under 2 MB) before reading them. Why: big images burn context and fail to load.
   - **Fable tier (Anmol 2026-11-10, limited budget).** Fable runs are few, so use them only where they matter most. Spawn the agent with `model: "fable"` for:
     1. Phase 0: the salvage audit, architecture discovery (ARCH_DISCOVERY and the architecture benches), and the planner's PLAN_PHASE for the first two phases after P0.
     2. Core system builds: the lane-level road model (lane sets, tapers and gores, flyover lanes; the top Fable task); the map repair layer rules (rule engine and auto-repair) and its elevation solver (`harness/design/MAP_REPAIR.md`); the road graph to junction and lane mesh builder (intersections, kerbs, railings, no overlaps); terrain that conforms to roads; the coordinate system and map bake pipeline; tile streaming and memory; the physics worker and vehicle handling model; the lighting, grade and render pipeline foundation; the area profile generator (procedural buildings and street dressing from area profiles, `harness/design/DELHI_WORLD.md`) and the landmark placement pipeline (Anmol 2026-11-10).
     3. Any task on its 3rd attempt, and any hard bug blocked twice.
     **Never Fable for** verifiers, content, art prompts, data, tooling, small fixes, polish or docs. Those stay on the normal tiers (Opus for look, animation and hard bugs; Sonnet for verifiers, tooling and small fixes).
     **Tagging:** the planner tags Fable tasks with the `model` field (`"model": "fable"` in add-json, `--model fable` on add, or `task.mjs model <id> fable`); `task.mjs show` and `next` print `MODEL fable`. Read the tag when spawning.
     **Budget:** `harness/state/fable_budget.json` holds `{"limit": N, "used": n}`. Before each Fable spawn check `used < limit`, then add 1 to `used` (edit the file, commit it with the task). When 3 or fewer runs are left, ask Anmol to raise the limit with a Needs-you notice (`node harness/bin/notice.mjs add "Fable budget: <n> runs left. Raise the limit?"`); his answer arrives in the inbox, where you update `limit`. Keep working meanwhile. When the budget is spent, spawn on Opus instead and note it on the task (`task.mjs note <id> "Fable budget spent, ran on Opus"`).
   - **Session log size:** when `task.mjs status` prints a `session log` line (over 15 MB, `sessionLogLimitMB` in kit.config.json), finish the in-flight task and tell Anmol a fresh session is due (`/clear`, then the goal prompt again). Why: every turn resends the log; a big one burns usage and can freeze the terminal.
   - On PASS or green: commit (`git add -A && git commit -m "[<id>] <title>"`), push, then `task.mjs done <id> --summary "<what changed; how verified>"`, and `task.mjs milestone <ID> playable` when a milestone passed. On FAIL: `task.mjs fail <id> --reason "<top problems>"` and go back to step 4 (the same task comes back with the notes; pass the report to the builder). After 3 failures the task is blocked: add a follow-up task with a different approach (smaller scope or another technique) and move on.
   - Content-writer and art-director tasks: check their output files exist and parse (`node -e "JSON.parse(require('fs').readFileSync('<file>','utf8'))"`), then commit and mark done.
   - **Play copy:** after marking tasks done and pushing, run `node harness/bin/playcopy.mjs --verified` so the dashboard /play/ serves the newest verified build. Why: builders rebuild and wipe `dist/` constantly; Anmol's open page needs a stable copy.
   - `verify.mjs --all` runs only at phase gates (`GATE <P>`, `GATE FINAL`).
   - **Camera and framing tasks:** write acceptance that covers every actor in the scene, the whole duration, and actors that move. The builder runs a 5-run flakecheck itself before reporting (3 in low usage mode). If a camera task fails its second attempt, the third attempt cuts scope to the simplest reliable fix (for example hold other actors still) rather than adding more scoring. Why: camera checks that pass on one still and fail on a moving actor were the most common repeat failure.
   - **Batching:** when the next 2 or 3 tasks in a phase are small, related, and their deps are done, give them to one builder run. Run `task.mjs start` for each, and mark each done separately with its own summary.
   - **Parallel** (only with ONE AGENT AT A TIME off): content-writer and art-director (and art-reviewer) tasks run in parallel with the builder, since they never touch src code. Still at most one builder at a time.
   - **Run ahead** (only with ONE AGENT AT A TIME off): while a builder works and no content-writer or art-director is running, keep the cheap tracks ahead: content-writer drafts dialogue for upcoming milestones in this phase and the next that have no dialogue file yet, and art-director writes prompts for the next phase's assets into `harness/requests/` as batches Anmol can make in one sitting. Check their files parse, then commit only those files (`git add <their files>`), never the builder's working tree.
   - **Verify on a snapshot** (with ONE AGENT AT A TIME on, the next builder waits for the verifier): when a builder reports, commit its work at once as `[<id>] <title> (verifying)`, run `node harness/bin/snapshot.mjs` (puts `.worktrees/verify` at that commit), and spawn the verifier with "work in .worktrees/verify: run verify.mjs and shoot.mjs from there and read shots from .worktrees/verify/harness/reports". While it checks, start the next builder in the main checkout, but only if the next task touches different files and systems than the one being verified; if they overlap, wait. Still one builder at a time. On PASS: `task.mjs done`. On FAIL: `task.mjs fail`; the fix goes on top as the next builder run (a revert commit if the work must come out); never rewrite history. Phase gates and the sweep still check the main branch. Why: the verifier judges a frozen commit, so the next builder's edits cannot change the verdict.
   - **Polish items from verifiers:** a verifier report may end with a POLISH list (cosmetic, close-up only; VERIFY.md "Severity rule"). They never fail a task. Collect them into one polish task per area in the last phase (`task.mjs add --phase <last> ...` or a note on an existing polish task).
   - **Speed rules:** `verify --quick` is the core set (about 20 to 30 scenarios) plus the scenarios mapped to the changed files (`harness/verify/quick.json`); the full set runs only at phase gates (and in sweeps if they are on). Builders run `--quick` once, at the very end. The verifier runs `freshreport.mjs --tree <main checkout>` in the snapshot and reuses the builder's quick run when the tree hash matches, then does only its own targeted runs, milestones and shots. Any new flake (fails, then passes with no code change) is a priority 1 bug task (low usage mode: noted unless it repeats at a gate). Builders read `docs/READ_MAP.md` sections for their area, not every doc. Why: most of a task's time went into repeated full runs that proved nothing new.
   - **Time-box tuning:** feel, balance, camera and look tuning gets one fix round and one test round per builder run; then the builder reports numbers and next steps instead of looping. Check on any builder that has run past 3 hours (its output file, `git status`), and stop it cleanly if it is looping. Why: open-ended tuning loops burned whole days without converging.
   - **Lane 2 (OFF by default):** a second builder may run in `.worktrees/lane2` (branch lane2, `node harness/bin/lane.mjs sync`) on tasks noted "Lane 2 task" (UI, menus, data, tooling, milestone flow), never touching the player, physics, movement or camera code. The lane builder does not run task.mjs or edit harness/state (it returns knowledge and decision lines in its summary; the orchestrator adds them). When it reports: commit inside the worktree as `[<id>] <title> (verifying)`, snapshot that commit with `snapshot.mjs <sha> --name verify2`, and spawn a verifier there. On PASS run `lane.mjs merge` (a normal merge into main; resolve small conflicts in shared files by hand), then `task.mjs done`, then `lane.mjs sync` before the next lane task. At most two builders: one main, one lane 2.
   - **Regression sweep only at phase ends:** no sweep mid-phase. The full `verify.mjs --all` runs at the phase gate (`GATE <P>`) only, so it never shares the machine with builders during a phase. To make up for it, when a task changes a shared system (in `shared_paths.json`), its verifier also replays the milestones that actually use what changed (find them with grep over src and the play scripts), at most about 6, plus the related `--only` scenarios. **Who replays milestones:** the full milestone replay is the verifier's job only. ### When something goes wrong

- Usage limit: Claude Code waits and continues automatically. After any resume, start at step 1.
- Tool or network failure (npm, Playwright download): retry up to 3 times with a short wait; if still failing, note it on the task (`task.mjs note`) and take another task. If the environment is broken for everything, add a priority-1 task "Fix environment: <problem>".
- A verifier keeps failing for the same reason across tasks: add a task to fix the root cause (tooling, test, shared system) before continuing feature work.
- A push fails: `notice.mjs add`, keep working, resolve the notice when a push works.
- The game breaks the hook contract (a refactor removed a hook): `hooks_contract` fails in quick; fix the hook before anything else (priority 1 bug).
- Context getting heavy: you lose nothing by compacting; all state lives in files. After compaction run step 1.

## Game facts (Dilli Darshan)

Dilli Darshan is an open-world driving game set in Delhi, built from real map data, with rich Delhi assets. Anmol's first request is in the inbox; Phase 0 handles it first.

**The old game is a READ-ONLY reference.** `/Users/apple/Desktop/code/delhi-drive` (a Barcelona OSM driving sim, originally Delhi). Never edit, build, install or commit in it. Read it only for the Phase 0 salvage audit and when checking a specific idea.

Lessons from the old game:
- It mirrored the world (`worldGroup.scale.x = -1`) and negated physics `px` to match. Collisions and visuals drifted apart and every system had to know about the flip.
- Roads were broken: overlapping road meshes, railings in the wrong places, junctions that did not join.
- Terrain and road fit was broken: roads floating over or sunk into the ground.
- `tileManager.js` grew to 2346 lines: one file owned streaming, building, physics and cleanup.
- Bake: `backend/worldBuilder/buildRegion.js` turned OSM PBF plus Copernicus GLO-30 DEM into binary 500 m tiles at zoom 16. The data sources and tile idea are worth auditing; the code is not trusted.
- Physics was Rapier WASM, with a leftover cannon-es descriptor layer still in the code.
- The Delhi tiles in `backend/tiles/delhi` are 11 GB in an old JSON format. Do not copy them; rebake from source data.
- The frontend has 580 node tests. Read them for intent (what was checked), not as proof the code works.

New-game rules:
- **One coordinate system.** East is +X, north is -Z, up is +Y, 1 unit = 1 metre. No mirroring anywhere, ever (no negative scale on world groups, no axis flips in physics). Tests from day 1: a known landmark lands at its projected position and the right side of the map, collision shapes match the visible meshes, north is up on the map and -Z in the world.
- **Copy from the old repo only after checking.** Anything taken from delhi-drive (code, data, tuning numbers, assets) is first checked and found to be the best way, and the decision is written to decisions.md with the reason.
- Do not trust the old code's base layer (roads, terrain, overlaps, railings, mirror axis). Rebuild those from first principles with tests.
